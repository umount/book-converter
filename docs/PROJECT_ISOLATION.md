# Design: Project Isolation, Parallel Runs, Save/Delete

Status: approved (full isolation + parallel). Old data may be discarded (no migration).

## Goal

Each open book is an independent **project**: its own data directory, database,
console log, progress, and translation job. Several projects can translate at the
same time. A project can be saved to a single portable archive and re-opened, and
deleted together with its data. Opening a book always creates a **new** project
(even the same file twice).

## Project identity

- A project has a stable **id** (a UUID generated by the frontend when the book is
  opened). Project identity is decoupled from the book's file path, so:
  - opening the same file again yields a separate project;
  - the id is the key everywhere (data dir, backend session, events, logs).
- The frontend keeps the project list (id, name, book path, ref path) in
  `localStorage` under a new key (`bc.projects.v2`); old path-based entries are
  ignored.

## On-disk layout

```
<app_data_dir>/
  settings.db                      # app-wide (UI language) — unchanged
  projects/
    <id>/
      progress.db                  # chapters, glossary, meta (per project)
      project.json                 # manifest: name, book path, ref path
```

Legacy flat `*.progress.db` files (old layout) are deleted on startup (allowed:
"can delete old data for compatibility").

## Backend: from one session to many

- `AppState(Mutex<HashMap<ProjectId, Session>>)` replaces the single `Session`.
- Every project-scoped command gains a `project_id` argument and operates on that
  entry (`map.entry(id).or_default()`). App-wide commands (`get_setting`,
  `set_setting`) are unchanged.
- Each `Session` already owns its `cancel`/`running`; with one per project, jobs are
  independent and may run concurrently. The DeepSeek client is stateless, so
  parallel runs only share the network/rate budget.
- The translation and retarget jobs run on their own OS thread (as today), one per
  project; the per-project `running` flag prevents two jobs on the *same* project.

## Events are tagged with the project id

Emitted payloads carry `project` so the frontend routes them to the right project's
log/progress even while several run at once:

- `progress` → `{ project, done, total, failed, pending, running }`
- `done` → `{ project }`
- `job_error` → `{ project, message }`
- `retarget_progress` / `retarget_done` / `retarget_warn` → include `project`

## Frontend: per-project console and progress

- `progress: Record<id, Progress>`, `logs: Record<id, string[]>`,
  `busy: Record<id, string|null>`. The console and progress show the **active**
  project; a project still translating in the background keeps updating its own log
  and shows a running indicator in the sidebar.

## Save / open a project archive (`.bcproj`)

A project archive is a zip bundle so a project is portable:

```
project.json          # { name, book_file, ref_file? }
progress.db           # the full per-project database
book.<ext>            # a copy of the source book (self-contained)
reference.<ext>       # optional copy of the reference
```

- `export_project(project_id, out_path)` — reads the source book bytes + the
  project's `progress.db`, writes the zip.
- `import_project(archive_path, new_id)` — extracts into `projects/<new_id>/`, sets
  the project's `source_path` to the extracted book, returns manifest info; the
  frontend registers a new project row.

## Delete a project

`delete_project(project_id)` removes `projects/<id>/` and drops the in-memory
session; the frontend removes the row and its logs/progress.

## Out of scope (for now)

- A global rate limiter across parallel runs (rely on DeepSeek's own 429 handling).
- Cross-machine sync.
